## 三、合同映射（user-record.schema.json @ b828553f）

迁移前只读核对了上游 `contracts/schemas/user-record.schema.json`
（本地克隆核对，HEAD 复验为 b828553f）。该私有接口**未**放入网站
public 目录。映射（完整注释在迁移文件内）：

| 合同字段 | 数据库 | 还原方式 |
| --- | --- | --- |
| user_id | `profiles.id`（= auth.users.id，uuid） | 直接 |
| completed_course_ids | `profiles.completed_course_ids`（text[]，元素非空 CHECK） | 直接 |
| confirmed_skills[].skill_id / source / source_id / confirmed_at | `user_skills` 行（skill_id 正则 CHECK；source ∈ course/experience/manual；`UNIQUE NULLS NOT DISTINCT (user_id, skill_id, source, source_id)`） | 每行一条 |
| experiences[].experience_id / text / created_at / updated_at | `experiences` 行（id=uuid 即 experience_id；text ≥1；updated_at 触发器维护） | 每行一条 |
| favorites[].target_type / target_id / created_at | `favorites` 行（target_type ∈ resource/opportunity；复合主键防同一用户重复收藏） | 每行一条 |
| learning_paths[].path_id / target_role_id / created_at | `learning_paths` 行（target_role_id CHECK 限定合同八枚举，逐字未改） | 每行一条 |
| learning_paths[].items[].item_id / resource_id / skill_id / status / updated_at | `path_items` 行（resource_id/skill_id 可空；status ∈ not_started/in_progress/completed） | 按 path_id 归组到所属用户的 learning_paths 条目 |

- 六个共同枚举全部按合同逐字实现为 CHECK 约束，未新增未改名。
- A1 无任何把候选技能写成已确认技能的路径（数据库与前端都没有）。
- `profiles.display_name` 是网站本地展示用便捷列，迁移注释明确标注
  **不属于合同导出字段**。

## 四、迁移与权限设计

`supabase/migrations/20261027000000_a1_personal_tables.sql`（已通过
`npx supabase db reset` 从零重放验证）：

- 主键/外键：全部个人表 user_id → `profiles(id)` ON DELETE CASCADE；
  profiles.id → auth.users(id) ON DELETE CASCADE（删除账号即清空其
  全部个人数据，已实测）。
- **双重所有权**：`learning_paths` 加 `UNIQUE (id, user_id)`，
  `path_items` 用复合外键 `(path_id, user_id) → learning_paths(id, user_id)`
  ——条目挂到他人路径在数据库层被拒绝，不依赖子表 user_id 检查。
- **user_id 默认值** `DEFAULT auth.uid()`：客户端无需传 owner；
  显式传他人 id 会被 RLS WITH CHECK 拒绝。
- 触发器：`handle_new_user`（security definer、固定 search_path）在
  注册时自动创建 profiles 行；`set_updated_at` 维护三表时间戳。
- **grants 最小化**：`REVOKE ALL … FROM anon, authenticated` 后仅
  `GRANT SELECT, INSERT, UPDATE, DELETE … TO authenticated`。
  anon（未登录）角色对六表**零权限**。
- **RLS**：六表全部 ENABLE，24 条策略（每表 SELECT/INSERT/UPDATE/
  DELETE 各一条，均 `to authenticated` 且 owner-scoped，使用
  `(select auth.uid())`）。UPDATE 策略 USING（原行）+ WITH CHECK
  （新行）同时限定 user_id，**禁止转移所有权**。path_items 策略额外
  要求引用路径属于本人。
- 无管理员角色、无客户端提权入口；普通用户 metadata 不作为授权依据
  （策略只看 auth.uid()，已实测）。

## 五、账户与会话（web/）

- `web/src/lib/supabase.ts`：仅凭 `VITE_SUPABASE_URL` +
  `VITE_SUPABASE_PUBLISHABLE_KEY` 创建浏览器客户端；未配置时返回 null
  （`SUPABASE_CONFIGURED=false`）。**只使用公开 publishable key**；
  service_role/secret 从不进入前端构建。
- `web/src/auth/AuthContext.tsx`：getSession 恢复刷新前会话 +
  onAuthStateChange 订阅；signUp 在需要邮箱确认时返回
  `confirmation-required`——页面明确显示"注册已受理……当前并未登录"，
  **不把受理当登录**；登录/退出走真实 Auth。
- `web/src/auth/useProfile.ts`：profiles 行按 user id 加载/保存，
  缓存严格绑定账号 id；账号切换立即丢弃上一账号缓存，迟到响应按
  cancelled 丢弃，不显示旧账号数据。
- `web/src/pages/Account.tsx`：未配置 → 明确"尚未配置 Supabase"并列出
  两个环境变量名，**无假用户、假 token、假登录**；已配置未登录 →
  登录/注册表单；已登录 → email、display_name、completed_course_ids
  保存与退出。
- 全部界面文本走中英字典（默认英文）；切换语言不清表单、不断会话、
  不改 canonical ID（浏览器实测）。
- 保留 A0：公共样例页、合同校验、SYNTHETIC 标记、中英切换均未改动
  （仅横幅/首页的阶段措辞从 A0 更新为 A0/A1）。
- 环境变量：`web/.env.example` 只有占位值；实际 `web/.env.local`
  （含本地栈 URL、publishable key、本地 secret key）已被 Git 忽略
  （`git check-ignore` 验证）。

## 八、人工复核步骤

1. 仓库根 `npx supabase start`（Docker 需运行），`npx supabase status`
   查看 URL 与密钥。
2. `npx supabase db reset` 验证迁移可从零重放；浏览器打开
   http://127.0.0.1:55423 （Studio）查看六表、24 条策略、anon 零权限。
3. 复制 `web/.env.example` 为 `web/.env.local`，填本地 URL 与
   publishable key，`npm --prefix web run dev`。
4. 注册一个自己的邮箱 → 在 http://127.0.0.1:55424 （Mailpit）点确认
   链接 → 登录、改资料、保存、刷新、退出、换号，观察数据隔离。
5. 跑隔离测试：
   `UTSC_SUPABASE_PUBLISHABLE_KEY=… UTSC_SUPABASE_SERVICE_ROLE_KEY=… npm run test:rls`
   （key 来自 `npx supabase status`，勿提交）。
6. 用 Studio 直接以某账号身份核对：任何账号在 SQL 编辑器里用
   `auth.uid()` 仅能看到自己的行（anon 未登录查询返回空）。
